## 修复"无法读取图片"（35 张失败图片诊断 + 回退解码）

- 用户问 update 日志里 35 张"无法读取图片"是否正常。诊断结论（三类）：
  1. **2 张 TGA**：cv2 根本不支持 TGA 解码（但 get_image_paths 扫描 .tga）。
  2. **约 14 张含巨型 iTXt 文本块的 PNG**：美术工具嵌入了 23MB~181MB 的 iTXt 元数据块，cv2 报 `user chunk data is too large` 拒读；其中 5 张 Pillow 也因解压超大块失败。
  3. **约 19 张根本不是图片**：16 张魔数 `c1832a9e` 的引擎私有格式（扩展名 .png 实为私有二进制）+ 4 张 Git LFS 指针文本文件（内容以 `version https://` 开头，美术资源未真正拉取）。
- 修复（dct_extractor.py::load_image 加两级回退）：
  - `_sanitize_png_chunks()`：解析 PNG chunk 流，剔除文本/元数据辅助块（iTXt/tEXt/zTXt/eXIf/tIME），保留关键块 + 色彩块（tRNS/gAMA/sRGB/sBIT/iCCP/cHRM）+ ≤64KB 无害辅助块；非 PNG 或数据不完整返回 None。
  - `_decode_with_pillow()`：Pillow 回退解码（覆盖 TGA），统一返回 BGR/BGRA/灰度（P→RGBA、非 RGB/RGBA/L→RGBA、RGB→BGR、RGBA→BGRA）。
  - 顺序：cv2(raw) → cv2(sanitized) → pillow(sanitized) → pillow(raw)。
- 实测 35 张：**16 张救回**（特征维度 4096 正常），19 张仍失败（确认非图片，跳过是正确行为）。
- 已知行为：失败文件永远进不了 valid_paths，每次 update 会被当作"新增"重试并告警（几十张开销 <1s，无害）；修复后 16 张会在下次 update 增量入库。建议美术侧处理 LFS 指针与私有格式文件。

## 修复"查询卡住"——CWD 相对路径 bug 触发全量重建（重要教训）

- 现象：GUI 查询卡在"查询中..."7~15 分钟，日志只有一行"正在初始化图片匹配系统..."。
- 根因链：用户把缓存目录改名 cache_time_test→cache 并改 settings.yaml cache_dir 为 ./cache；从 webapp/ 目录启动服务器（`python server.py`）时进程 CWD=webapp/，而 **src/main.py 的 cache_dir 相对路径按 CWD 解析** → 找 webapp/cache（不存在）→ 查询的进程内初始化触发全量重建（特征提取→RF→聚类），且日志在服务器进程里被丢弃（root logger 无 handler，INFO 静默），用户完全看不到进度。
- 发现过程：诊断时 webapp/cache/dct_cache 已有 57253 个文件（更早一轮重建的产物），index 17:57:49 写完——重建其实完成了。另发现 os.execv 在 Windows 残留了第二个僵尸 server.py 进程。
- 修复（三处）：
  1. **src/main.py**：新增 `resolve_cache_dir()` 静态方法——相对 cache_dir 以 config 文件上一级（项目根）为基准解析，load_clustering_system 使用之。CLI 与进程内行为从此与 CWD 无关。
  2. **webapp/server.py**：`os.execv` 改为 `subprocess.Popen + sys.exit(0)`（避免 Windows 双进程）；main() 里 `os.chdir(PROJECT_ROOT)`；给 root logger 加 StreamHandler（INFO），src 初始化日志可见，不再"静默卡住"。
  3. 缓存归位：webapp/cache（最新：57253 张、含 16 救回、不含 19 已删，index 17:57:49）移到项目根 cache/；旧 cache 改名 cache_old 留存（用户取消删除，~57k 文件，确认后可手动删）。
- 验证：从 webapp 目录模拟启动，get_query_api() 初始化 3.6s（仅 BallTree 重建日志，无全量重建），查询 0.10s 返回 success；真实 HTTP 服务器 status 200 + query success 0.09s。
- 教训：webapp 的 resolve_cache_info（PROJECT_ROOT 基准）与 src/main.py（CWD 基准）曾不一致——修复后两者都以项目根解析；以后凡相对路径必须锚定项目根。

## CPU 多核利用情况分析（用户询问，并行化已于同日完成）

- 机器：20 逻辑核心。
- **特征提取（最大瓶颈）完全串行**：`dct_extractor.py::get_dct_features` 是 `for` 循环逐张处理（imdecode→cvtColor→resize→DCT→CRC32→pickle 缓存），无任何 multiprocessing/joblib/线程池；57k 张图首次构建会非常慢。
- **特征选择**：随机森林 `RandomForestClassifier(n_jobs=-1)` 用满多核（feature_selector.py:110，全项目唯一显式并行点）。
- **聚类**：>10000 样本走 MiniBatchKMeans（sklearn 该实现基本单核）；≤10000 走 KMeans（内部 OpenMP 多线程）。BallTree 逐簇串行构建。
- 优化机会：给 `get_dct_features` 加 `multiprocessing.Pool`（进程池）或 `joblib.Parallel`，按图片分片并行；每张图独立（读→算→写自己的 .pkl 缓存），天然适合并行，预期 10-16 倍加速。注意 Windows 需 `if __name__ == '__main__'` 保护/函数需可 pickle（staticmethod 无 self，可行）。
